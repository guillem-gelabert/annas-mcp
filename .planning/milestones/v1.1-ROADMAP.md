# Milestone v1.1: Mirror Resilience

**Status:** ✅ SHIPPED 2026-05-19  
**Phases:** 5–7  
**Total Plans:** 3  

## Overview

Made `annas-mcp-ts` resilient to Anna's Archive mirror/base URL changes. Added automated Wikipedia-based discovery with revision trust logic, a server-side JSON cache, and offline recovery paths for both manual and automatic base URL configurations. Exposed the discovery/refresh flow as an MCP tool (`update_base_url`) alongside the existing article tools.

## Phases

### Phase 5: Wikipedia Base URL Discovery

**Goal:** Build a tested discovery module that can find Anna's Archive candidate base URLs from Wikipedia and only trust links with 24-hour revision evidence.

**Requirements:** WIKI-01, WIKI-02, WIKI-03, WIKI-04, WIKI-05

**Plans:**

- [x] 05-01: Implement Wikipedia revisions-driven base URL discovery

**Details:**

- Revisions API ingestion with bounded scan limits (`REVISION_LIMIT=200`, `LOOKBACK_MS=14d`)
- Host extraction and strict `annas-archive.*` filter via `HOST_PATTERN` regex + Set deduplication
- Trust logic: candidate must be in latest revision and one revision older than 24 hours
- Unit coverage in `tests/base-url.test.ts`

**Success Criteria:**
1. Discovery extracts candidate links from the user-specified Anna's Archive infobox selector. ✅
2. Candidate normalization produces base URL values compatible with existing Anna's Archive URL construction. ✅
3. Malformed, duplicate, non-http(s), and non-Anna's-Archive-looking links are skipped with structured reasons. ✅
4. Revision-history checks prove accepted candidates existed at least 24 hours before refresh time. ✅
5. Bounded revision scanning returns clear skipped/error states when candidate age cannot be proven. ✅

### Phase 6: Base URL Cache and Selection

**Goal:** Add a low-tech server-side cache and effective-base-URL resolver that uses discovery only when no manual `ANNAS_BASE_URL` is set.

**Requirements:** CACHE-01, CACHE-02, CACHE-03, CACHE-04, CACHE-05

**Plans:**

- [x] 06-01: Implement base URL cache and runtime resolver

**Details:**

- JSON cache read/write in user cache directory (`~/.cache/annas-mcp-ts/base-url-cache.json`)
- Manual override flag (`manualBaseUrl`) in config loading
- Runtime resolver path: manual first, cache/discovery for automatic mode
- Test validation for manual override short-circuit and cached discovery updates

**Success Criteria:**
1. Trusted discovery results are persisted in a local JSON cache with evidence metadata. ✅
2. Runtime base URL resolution uses the manual env var when `ANNAS_BASE_URL` is set. ✅
3. Runtime base URL resolution uses cached/discovered values when `ANNAS_BASE_URL` is unset. ✅
4. Cache read/write failures are visible in structured output and never corrupt MCP stdout. ✅ (write side; read side silently falls through — see tech debt)
5. README/code clearly distinguishes server cache from MCP client-side `ttlMs`/`cacheScope` hints. ✅

**Success Criteria:**

**Tech Debt Incurred:**
- `WIKIPEDIA_SELECTOR` constant is documentary only; extraction uses full-wikitext regex (not CSS)
- `readCache()` swallows errors silently (only write errors surfaced)
- Offline automatic retry path has zero test coverage

**Key Decisions:**
- `ANNAS_BASE_URL` remains the winning manual override when set
- Automatic mirror discovery uses trusted Wikipedia candidates with 24-hour revision evidence
- Mirror resilience uses internal server-side JSON cache (not MCP client-side cache hints)
- Per-invocation `BaseUrlManager` instantiation (stateless; shared cache via disk file)

**Issues Resolved:**
- Anna's Archive mirror instability addressed with Wikipedia-backed discovery
- Manual override offline scenario now surfaces actionable MCP guidance

**Issues Deferred to v1.2:**
- Fix `WIKIPEDIA_SELECTOR` misleading metadata (use wikitext regex documentation or implement HTML parsing)
